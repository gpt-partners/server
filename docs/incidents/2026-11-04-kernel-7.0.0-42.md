# Incident 2026-11-04: LiteLLM down after kernel 7.0.0-42

- Impact: LiteLLM (the LLM gateway for all apps) did not start for about 60 hours,
  2026-11-04 ~07:50 to 2026-11-06 ~20:10 UTC. Other workloads kept running.
- Root cause: the automatic upgrade to Ubuntu kernel 7.0.0-42-generic.
- Fix: boot 7.0.0-38-generic and pin it; block 7.0.0-42/-43 in unattended-upgrades (#34).
- Decision taken from it: [ADR 0001](../adr/0001-kernel-updates.md).

## What happened

unattended-upgrades installed kernel 7.0.0-42 and rebooted the node on 2026-11-04 around 05:00 UTC.
From then on LiteLLM hung at every start: the Prisma CLI (Node.js) and its schema-engine (Rust) stopped
without an error, the startup probe killed the pod after about 650 s, and timeouts meant to end the
hang did not work. The hang happened with and without the database: in the last tests the
schema-engine had no network connection at all.

The same morning Renovate updated LiteLLM to v1.108.0 (gpt-partners/platform#61). That looked like the
cause, so two days went into the image, the database and the Supabase pooler. Rolling back the image
did not help, because the kernel was the same.

The exact mechanism is not proven. A report for this kernel describes an AppArmor signal regression
in containers ([Cumulocity](https://community.cumulocity.com/t/cumulocity-iot-edge-startup-failure-on-ubuntu-kernel-7-0-0-42-generic/15332)).
A `sleep 30 & kill $!` test in the pod failed on both kernels, so it does not tell them apart.
What is proven is the link to the kernel: LiteLLM hung after every boot into 7.0.0-42 (2026-11-04,
2026-11-06 20:03 and 21:35) and ran after every boot into 7.0.0-38 (2026-11-06 ~20:10 and ~21:50).

## What went well

- Grafana (`node_uname_info`, `node_boot_time_seconds`) showed the kernel change as soon as we looked.
- Reading the database side in Supabase ruled the database out quickly.

## What went badly

- Nobody looked at what changed on the node itself until day three.
- The Renovate update on the same morning was a convincing false lead.
- A Loki query with the wrong label (`namespace` instead of `k8s_namespace_name`) made it look as if
  there were no logs.
- A node command was first run on the wrong machine; check `hostname` before node commands.

## Follow-ups

- [x] Block kernels 7.0.0-42/-43 in unattended-upgrades (#34)
- [x] Revert the LiteLLM workarounds (platform#93, #94, #95)
